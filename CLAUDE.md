# CLAUDE.md

Guidance for Claude Code (claude.ai/code) when working in this repository. User-facing setup lives in `README.md`; this file holds what you need to change the code safely.

## What this is

OpenPrism is a local-first LaTeX + AI workspace for academic writing: a three-panel web app (file tree / CodeMirror LaTeX editor / PDF preview) with an LLM assistant (chat/agent/tools modes), LaTeX compilation, template management, LLM-powered template transfer (migrating a paper between conference templates), real-time multi-user collaboration (Yjs CRDT), and peer-review tooling.

**Stack:** React frontend + Django REST/Channels API + Celery workers + Postgres + Redis + Garage (S3), run locally with `docker compose` and in Kubernetes via the Helm chart in `deploy/helm`. The former Node/Fastify backend is gone (see git history before the Phase 7 commit). **Production runs on the cent cluster (https://openprism.cent-su.org); the version is in `apps/api/VERSION` and `/api/health`, and a `vX.Y.Z` tag deploys it.** What is still unverified there is listed in `deploy/helm/README.md` ("Unverified") and tracked as GitHub issues; read both before trusting it.

## Running and testing

Develop inside the devcontainer (Node 20, TeX Live, docker-in-docker so `docker compose` works). Forwarded ports: 5173 (Vite), 8080 (nginx app), 8000 (API), 5432, 6379, 3900.

```bash
cp .env.sample .env                 # once; add OPENPRISM_LLM_* / OPENPRISM_MINERU_TOKEN for server-side AI defaults
docker compose up -d --wait         # postgres, redis, garage, api, worker-tex, worker-ai, beat, web
deploy/garage-init.sh               # idempotent: Garage layout, bucket, access key, bucket CORS (reads S3_* from .env; needs the api running)
npm install
npm run dev                         # Vite on :5173, proxies /api + websockets to the api on :8000
```

- **Use the app** at http://localhost:5173 (hot reload) or http://localhost:8080 (the production `web` image). Register an account in the UI; there is no seeded user.
- **Legacy data:** `docker compose exec api python manage.py import_legacy --owner you@example.com` loads `data/` (mounted read-only at `/legacy/data`; the built-in templates need no mount, see *Templates*) into an account. Register that account first.
- **API tests** (real Postgres/Redis/Garage; run `deploy/garage-init.sh` once first; always pass `--noinput`, since a stale `test_openprism` database otherwise blocks on a prompt):
  - `docker compose run --rm api python manage.py test --noinput` (LaTeX/plot tests skip here)
  - `docker compose run --rm worker-tex python manage.py test jobs transfer --noinput` (real pdflatex/bibtex)
  - `docker compose run --rm worker-ai python manage.py test ai --noinput` (real matplotlib + plot sandbox)
- **Browser tests** (Playwright, `apps/frontend/e2e`): with the stack and `npm run dev` running, `npm run e2e` from the repo root (`E2E_BASE_URL=http://localhost:8080` tests the nginx image). The devcontainer image ships Playwright's Chromium and Google Chrome (`PLAYWRIGHT_BROWSERS_PATH=/ms-playwright`; versions pinned in `.devcontainer/Dockerfile`, keep `PLAYWRIGHT_VERSION` equal to `@playwright/test`), so there is nothing to install. `E2E_BROWSER=chrome` runs in real Chrome; the container has no display, so headless is the default and `xvfb-run -a` with `E2E_HEADED=1` gives a headed run. Each test registers its own account and project. Add a spec for any UI behaviour you change, and check that it fails on the old code. To QA an acceptance criterion by hand, write a throwaway script against the same browsers (`npx playwright` / `chromium.launch()`), and look at screenshots.
- **CI** (`.github/workflows/ci.yml`, GitHub Actions): every push and pull request runs `npm run typecheck`, the Helm chart lint and render, the Caddy config validation and ShellCheck of the deploy scripts, the API suite and the AI-worker suite; pushes and pull requests to `main` and `release/*` also build the TeX worker and run its suite and the full browser suite against the compose stack on :8080 (the `web` image), uploading the Playwright report and `docker compose logs` when it fails. The composite action `.github/actions/stack` writes a `.env` from `.env.sample` with fresh secrets, builds the services with `docker buildx bake` (layer cache in the GitHub Actions cache, tagged `openprism-<service>` so `compose up` reuses them), starts them and runs `deploy/garage-init.sh`; the browser job also loads the built-in templates (`import_legacy --skip-projects`) and raises `AUTH_RATE_LIMIT` (compose passes it through, default 20/min), since every test registers accounts from one address. The compose Redis has 16 databases, so the tests' database 15 needs nothing; a CI Redis with only one database needs `TEST_REDIS_URL`.
- **Logs / restarts:** `docker compose logs -f api worker-tex`. Celery does not auto-reload: after editing task code run `docker compose restart worker-tex worker-ai beat`. The api reloads itself (code is bind-mounted). After rebuilding an image use `docker compose up -d` (not just `build`) so containers are recreated.
- **Reset / migrations:** `docker compose down` keeps volumes (`-v` wipes all data). After model changes: `docker compose run --rm api python manage.py makemigrations <app>` and commit the migration. **A non-null column added to an existing table needs `db_default=` as well as `default=`** (`common/test_migrations.py` fails otherwise): during a rolling deploy the previous release's pods keep inserting rows without the new column, and only a database default lets those inserts succeed. After migrating in compose, restart the workers (`docker compose restart worker-tex worker-ai beat`) so they run the new code. `docker compose up` runs `migrate` on every api start (fine for dev; in k8s it is a one-off Job).
- **Health:** `curl localhost:8000/healthz` (liveness), `localhost:8000/readyz` (Postgres + Redis + S3; 503 otherwise), `localhost:8080/healthz` (web).
- **Version:** the single source is `apps/api/VERSION` (semver, no `v`). The API returns it from `/healthz` and `/readyz`, Vite injects it as `__APP_VERSION__` (shown at the bottom of the account menu), and the web Dockerfile copies the file in. Bump it on the release branch; git tags are `vX.Y.Z` (`v0.0.0` is the pre-versioning baseline).
- Use plain `docker compose`, not npm wrappers. `npm run build` / `npm run preview` only build/preview the frontend.
- **Clock steps.** In the devcontainer (WSL2) the wall clock steps back about a second several times a minute, so a JWT minted just before a step has an `iat` in the future. Without leeway SimpleJWT refuses it ("Token is invalid") and unrelated tests fail at random; `JWT_LEEWAY_SECONDS` is 5 under the test runner and in `compose.yaml` for that reason, and must stay 0 (unset) in production and Kubernetes.
- **Bind mounts and git.** The api/worker containers bind-mount `apps/api` and the data services mount single files. Anything that deletes and recreates those paths (e.g. checking out a branch that lacks them, then switching back) leaves containers pointing at deleted directories: `docker exec` fails with "current working directory is outside of container mount namespace root", health checks go unhealthy, and services keep running old code. Fix: `docker compose up -d --force-recreate`.
- **Static checks:** there is no JS test suite and no lint/format config. `npm run typecheck` (`tsc --noEmit` in `apps/frontend`) reports no errors; keep it that way (CI runs it). For UI changes, verify in a real browser (Playwright can be installed outside the repo: `npm i playwright` in a scratch dir). Vite uses file polling because the bind-mounted workspace does not deliver change events.
- LaTeX compile needs a TeX engine; only the `worker-tex` image carries full TeX Live (the devcontainer has `latexmk` + a subset of `texlive-*`).

## Conventions
- Requirements live in `docs/` (plans live in GitHub issues). If a request contradicts them, say so rather than guessing.

- Commit messages say what was decided, not just what changed. "Update file" is never acceptable.

## Instructions for Claude

1. **GitHub issues are the only tracker** (`docs/backlog.md`, `docs/todo.md` and `docs/xchangelog.md` are retired; the changelog is frozen history). New bugs, ideas and requests (including ones users file with the issue forms) start as an issue labelled `status:backlog`, or `triage` when a user filed it. Always pass `-R cent-ischool/OpenPrism` to `gh`: its default repository is the upstream fork.
2. **The current release is a milestone** (`vX.Y.Z`): its open issues are the todo list. Finish them before starting the next release's issues. Release notes are the milestone's closed issues; no file needs updating when an issue closes.
3. We don't write code unless there is a GitHub issue for it.
4. Scheduling an issue means giving it the release label (`vX.Y.Z`, green `Epic:` label) **and** the matching milestone, and removing `status:backlog`.
5. All GitHub issues should be well-defined so a programmer of moderate ability can complete the task trivially.
6. All GitHub issues should have acceptance criteria and definition of done sections, suitable for a product manager.
7. Every issue has exactly one priority label (`priority:P0` security/data loss/outage, `P1` next release, `P2` soon, `P3` nice to have) and one type label (`type:bug|feature|chore|security|ops|docs`), plus the existing area labels (`authentication`, `deploy`, `collab`, ...).
8. Do not wander off task. If you encounter a bug, feature or enhancement idea while working, open an issue for it (`status:backlog`, priority, type) and carry on.
9. Code in a `dev/<issue>-<slug>` branch cut from the current release branch (`release/vX.Y.Z`) and merge it back with `--no-ff`. The release branch merges to `main`, tagged, when every issue in it is closed.
10. We test the code we write. Unit and integration tests.
11. An issue is not done until tests pass, the server runs and the app runs without error. Use Playwright to QA features as part of the verification of accepatance critieria as appropriate.
12. When an issue closes, say in its closing comment which commit or PR fixed it and how it was verified.
13. Start each issue from the release branch with a clean working directory.



### Workflow with GitHub issues

All commands use `gh ... -R cent-ischool/OpenPrism`.
- **Triage.** Users file issues through the forms (`triage` label plus `type:bug` or `type:feature`). Read it, reproduce bugs, ask for what is missing, set one `priority:*` and one `type:*`, add area labels, then either schedule it (release label and milestone, no `status:backlog`) or mark it `status:backlog`; remove `triage`. Close duplicates and invalid reports with a reason. A `priority:P0` issue goes into the current release at once.
- **Set up a release.** Create the label (`vX.Y.Z`, colour `0e8a16`, description `Epic: <theme>`) and the milestone of the same name, then schedule issues into it (rule 4). The last issue of every release is `Release vX.Y.Z` (version bump in `apps/api/VERSION`, Helm/workflow/runbook changes, docs).
- **Work an issue.** Follow rules 3-13: branch `dev/<issue>-<slug>` from `release/vX.Y.Z`, put `(#<issue>)` in the commit message, merge back with `--no-ff`, close the issue with a comment naming the commit and how it was verified.
- **Close a release.** When the milestone has no open issues: merge `release/vX.Y.Z` to `main` with `--no-ff`, tag `vX.Y.Z` (the tag deploys to the cent cluster, so only when the user asks), close the milestone, and publish the release notes from its closed issues (`gh release create vX.Y.Z --generate-notes` or a list of the milestone's issues). Merging a release branch to `main` without a tag (e.g. to publish docs or issue forms early) does not deploy.
- **Unscheduled work** (`status:backlog`) has no milestone; it is reviewed when the next release is planned.

## Configuration

Everything is environment variables. `.env` at the repo root (copied from `.env.sample`, gitignored) is passed into the devcontainer via `runArgs --env-file` and read by compose for `${VAR}` interpolation. Compose supplies container-side URLs (`postgres`, `redis`, `garage`) itself, so `.env` values like `DATABASE_URL=...@localhost` are for tools running in the devcontainer, not for compose services.

- **API and workers** (`apps/api/config/settings.py`): `DJANGO_SECRET_KEY` (**required, no default; startup fails without it**), `DJANGO_DEBUG`, `DJANGO_ALLOWED_HOSTS`, `DATABASE_URL`, `REDIS_URL` / `CELERY_BROKER_URL`, `S3_ENDPOINT_URL` (internal), `S3_PUBLIC_ENDPOINT_URL` (browser-reachable; used in presigned links), `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `JWT_ACCESS_MINUTES`, `JWT_REFRESH_DAYS`, `JWT_LEEWAY_SECONDS` (clock difference tolerated on token times: 0 by default, 5 under tests and in compose; see *Clock steps* below), `CREDENTIAL_ENCRYPTION_KEY` (**required**; comma-separated Fernet keys, first encrypts, all decrypt, so rotate by prepending; losing it makes stored Zotero keys unreadable), `ZOTERO_API_BASE` (tests point it at `FakeZotero`), `VERSION_KEEP_UNNAMED` (default 50: unnamed successful project versions kept per project), `VERSION_KEEP_FAILED` (default 10: unnamed failed-compile versions, counted apart), `AI_EDIT_RATE_PER_MINUTE` (default 20: in-place AI edit requests per user), `AI_RATE_PER_MINUTE` / `COMPILE_RATE_PER_MINUTE` (default 30 each: per user, guests per invite; AI covers llm, agent, vision, plot, transfer start and arXiv import; 429 with `Retry-After`), `SERVER_LLM_KEY_USERS` (`all` default in compose, `verified` in k8s, `staff`, `none`: who may run AI jobs on the workers' `OPENPRISM_LLM_*` key) and `SERVER_LLM_DAILY_QUOTA` (default 200 such jobs per user per UTC day, 0 = no limit), `LLM_USAGE_KEEP_DAYS` (400). `ADMIN_SESSION_HOURS` (8) and `ADMIN_LOGIN_RATE_PER_15_MIN` (10 login form submissions per client address; see *Django admin*). `REQUIRE_EMAIL_VERIFICATION` (default off), `REGISTRATION_MODE` (`invite` by default, `open` for anyone; the test runner and compose default to `open`), `WORKSPACE_INVITES_ALLOW_SIGNUP` (1: in invite mode a workspace invitation also opens the door), `PLATFORM_INVITE_DAYS` (7), `ACCESS_CONTACT_EMAIL` (shown on the closed sign-up pages), `SOCIAL_GOOGLE_CLIENT_ID/_SECRET`, `SOCIAL_ORCID_CLIENT_ID/_SECRET`, `ORCID_SANDBOX`, `PASSKEY_RP_ID`, `SIGNIN_KEEP_DAYS` (v0.1.4; Helm `secrets.SOCIAL_*`, `social.orcidSandbox`), `SUPERADMIN_REQUIRE_MFA` (v0.1.3: on by default, off in compose and under tests; Helm `auth.superadminRequireMfa`); Helm: `registration.*`. **Mail:** `APP_BASE_URL` (origin used in links; required unless debug), `EMAIL_HOST`/`EMAIL_PORT`/`EMAIL_HOST_USER`/`EMAIL_HOST_PASSWORD`/`EMAIL_USE_TLS`/`EMAIL_USE_SSL`/`DEFAULT_FROM_EMAIL` (Django SMTP; compose points at the `mailpit` service, web UI and API on :8025; tests use the locmem backend). Settings parse `DATABASE_URL` themselves (no django-environ); add new config via `env()` / `env_bool()`. The `.env.sample` values (all-zero Garage secrets, `dev-insecure-change-me`) are dev placeholders: never reuse them on a shared deployment.
- **Frontend** keeps no API keys. A user's own AI keys (LLM, search, vision, MinerU) are stored on the server, encrypted like the Zotero key (v0.0.8, `integrations/userkeys.py`), and the UI's requests only name a `profile`; `openprism-settings-v1` (localStorage) now holds only non-secret settings (compile engine), and `app/legacyKeys.ts` moves keys an older build left there to the server once and deletes them. Stored credentials (users' AI keys, Zotero keys, workspace providers) are encrypted at rest with `CREDENTIAL_ENCRYPTION_KEY` and never returned by any endpoint (only their last four characters). Account session (v0.0.8): the refresh token is the httpOnly cookie `openprism_refresh` (path `/api/auth`, SameSite=Strict, `Secure` unless `DEBUG` or `REFRESH_COOKIE_SECURE=0`) and the access token lives in memory only; `openprism-auth-v1` is an older build's localStorage entry, migrated once and deleted. `TRUSTED_ORIGINS` (comma-separated, besides `APP_BASE_URL`; compose adds `http://localhost:8080`) are the origins that may use the cookie; `AUTH_REFRESH_RATE_LIMIT` (120/min per address: every tab refreshes on load). Invite token: `openprism-collab-token` (sessionStorage). Live-editing display name: the account's name unless the person typed one, kept as `openprism-collab-name:<userId>` (invite guests: `openprism-collab-name`, default "Guest").
- New dependencies go in `apps/api/requirements.txt` as exact pins, then `docker compose build api`. Test-only ones go in `requirements-dev.txt`: the compose `api` and `beat` services build the Dockerfile's `dev` stage (the `api` stage plus those), while production images (built by the deploy workflow: Dockerfile targets `api`, `tex`, `ai`) carry neither them nor any `tests.py`/`test_*.py` (deleted at build; compose bind-mounts the source, so the suites still run there).

## Architecture

Monorepo: `apps/frontend` (React 18 + TypeScript + Vite; the only npm workspace), `apps/api` (Django + Celery + Channels, built from `apps/api/Dockerfile`), and `design/` (shared UI package imported as `@design`). `compose.yaml` runs everything locally.

### Components (one image/Deployment each in k8s)

| Component | Tech | Role |
|---|---|---|
| `web` | nginx + built frontend (`apps/frontend/Dockerfile`, `nginx.conf`) | Serves the SPA (history fallback, hashed assets cached), proxies `/api` incl. websockets and SSE to `api:8000`, 200 MB uploads, and `/admin/` + `/static/` (the Django admin and its CSS/JS, v0.1.1: `no-store`, and Referrer-Policy `same-origin` there, because under `no-referrer` browsers send `Origin: null` on the login form and Django's CSRF check refuses it). Logs omit query strings (short-lived scoped URL tokens travel in `?token=` for images/PDFs/event streams/websockets) and it sends `Referrer-Policy: no-referrer` so they cannot leak. Build context is the repo root (the frontend imports `/design`) |
| `api` | Django + DRF + Channels, uvicorn (ASGI) | Stateless REST **and the collab websocket** (`/api/collab`); `/healthz`, `/readyz`; the Django admin at `/admin/` with its static files served by WhiteNoise (collected into `/app-static` when the image is built; debug and tests read the apps' files directly; `CSRF_TRUSTED_ORIGINS` = `TRUSTED_ORIGINS`). Scales horizontally: replicas sync through Redis, no sticky routing |
| `worker-tex` | Celery, queues `compile` + `transfer` | TeX Live image (template transfer compiles LaTeX and also calls LLM/MinerU). Per-command timeout, CPU/file-size rlimits, shell-escape off. Set container CPU/mem limits in k8s |
| `worker-ai` | Celery, queues `ai` + `import` | LLM, vision, plot (runs LLM-generated Python), agent, arXiv import. Image adds matplotlib/pandas/seaborn (`requirements-ai.txt`) |
| `beat` | Celery beat | Reaps jobs whose worker died, deletes finished jobs after 24 h, clears expired admin sessions daily, removes expired collab invites, saves the update logs of dead collab replicas every minute |
| `postgres`, `redis`, `garage` | | In `compose.yaml`; managed services/operators in k8s |

Design rules: services are stateless and 12-factor (env-only config, no shared volumes; workers materialise project files into a temp dir), long operations become `Job` rows + Celery tasks that the frontend polls, and nothing user-visible depends on local disk.

### Django API (`apps/api`)

Apps: `accounts` (email-login `User`, register/login/refresh/me), `projects` (`Workspace`, `Membership`, `Project`, `ProjectFile`, file service, REST views), `templates_app` (`Template` + S3 template files), `jobs` (`Job` model, compile service + tasks, job API), `ai` (LLM client, agent, plot sandbox, arXiv, AI task + endpoints), `transfer` (template-transfer engine, nodes, MinerU client, endpoints), `collab` (invites, guest auth, Yjs rooms, websocket consumer), `integrations` (Zotero: encrypted key store, API client), `versions` (project version history), `common` (health, `{ok,error}` exception handler, path-preserving multipart parser, safe zip reader). `config/` has settings, urls, asgi, and the Celery app.

**Data model.** `Project` (name, tags, archived, trashed/trashed_at, `file_order` JSON) belongs to a `Workspace`; users reach projects through `Membership` roles (`owner`/`admin`/`editor` can write, `viewer` is read-only). Registering creates a personal workspace. A non-member gets **404, not 403**, so project existence is not revealed.

**File storage: go through `projects/files.py`, never touch `ProjectFile` rows or S3 directly.** Text files (by extension, see `projects/paths.py`) live in Postgres (`ProjectFile.content`); binaries live in Garage under random keys `projects/<projectId>/<uuid>`, so renames are DB-only; templates live under `templates/<id>/`. Directories are implicit from path prefixes (explicit `dir` rows exist only for empty folders). Always validate user paths with `safe_path()` (rejects absolute paths, `..`, NUL) or `sanitize_upload_path()` (lenient, for uploads/zips). The service refuses to put a file under a file or replace a directory.

**API conventions** (match `apps/frontend/src/api/client.ts`; change client and server together):
- Errors are `{ok: false, error: "<message>"}`. Business errors (missing name, tags not an array, delete of a missing file) return HTTP 200 with that body; auth/permission/not-found/bad-path use real status codes.
- Project meta is camelCase (`createdAt`, `updatedAt`, `trashedAt`, `fileOrder`, `workspaceId`), ISO timestamps ending in `Z`.
- Auth is `Authorization: Bearer <JWT>`. `?token=` (for `<img>`/`<object>`/EventSource/WebSocket, which cannot send headers) accepts **only a URL token** (v0.0.8, `common/urltokens.py`): `POST /api/url-token {scope: project, projectId} | {scope: import}` (header credentials only; members and that project's invite guests; `import` for accounts) returns `{token: "ut1.…", expiresAt, expiresIn}`, a signed, timestamped token naming its principal and scope that lives `URL_TOKEN_SECONDS` (3600). `projects.access.UrlTokenAuthentication` accepts it on the blob, version PDF/file, job PDF and arXiv import endpoints, puts its `UrlClaims` in `request.auth`, and `get_project()` / `allows_project()` hold it to its one project; the principal (membership, invite) is re-checked on every use. An access token or invite token in a URL is refused (401). The blob endpoint responds with `Content-Security-Policy: sandbox` so uploaded SVG can't run script.
- Folder uploads send relative paths in the multipart *filename* (`form.append('files', file, 'figs/a.png')`). Django normally strips this to a basename; `common/uploads.py` preserves the sanitised path as `file.full_path`, read via `upload_path()`. In tests build such bodies by hand (the Django test client strips paths too; see `multipart()` in `projects/test_api.py`).
- **Direct uploads** (v0.0.8, `projects/direct_uploads.py`, `S3_DIRECT_UPLOADS`, on in compose, off in k8s because the cluster's MinIO is not browser-reachable, issue #116): `POST /api/projects/:id/uploads {files:[{path, size, contentType}]}` (write access, editor guests too) validates the whole batch (paths sanitised like the multipart upload, `MAX_UPLOAD_BYTES` 200 MB, ≤500 files, the usual tree rules) and returns per binary file a presigned PUT URL (15 min, Content-Type signed) for a fresh key, recorded as a `PendingUpload`, and `direct: false` for text files (they still go to `/upload`); with the setting off it answers `{ok, direct: false}` and the client uses `/upload` for everything. The browser PUTs to S3, then `POST …/uploads/complete {uploadIds}` HEADs each object (missing or not the declared size: deleted, reported in `failed`) and registers it with `files.register_binary()`; only the uploader (account or invite) can complete. The beat task `projects.tasks.cleanup_pending_uploads` (every 15 min) removes uploads never completed after an hour, with their objects. The bucket needs CORS for the app's origins: `manage.py configure_s3_cors` (run by `deploy/garage-init.sh`; one rule per origin from `APP_BASE_URL` + `TRUSTED_ORIGINS`, because Garage answers a preflight with all of a rule's origins joined and matches header names case-sensitively). Client: `uploadFiles()` in `api/client.ts` (XHR PUT with progress). Template ZIP upload and project ZIP import still go through the API. Browser tests: `e2e/direct-uploads.spec.ts`.
- Presigned URLs are signed for `S3_PUBLIC_ENDPOINT_URL`, so tests fetch them through the internal endpoint with the public `Host` header.
- Behind proxies, set `TRUSTED_PROXY_COUNT` to the number of proxies in front of the API (compose: 1, Kubernetes: 2); otherwise all users share the proxy's address and the login rate limit.

**Async jobs (compile).** Long work is a `Job` row plus a Celery task; the API never blocks on it. `POST /api/compile {projectId, mainFile, engine}` validates, then returns `{ok, jobId}` (max 3 active compiles per user → 429). `GET /api/jobs/:id` returns `{status: queued|running|success|failed, progressLog, error, result}` (`result` = `{log, status, engine, mainFile, pdfUrl}` once finished). `GET /api/jobs/:id/pdf` streams the PDF from Garage through the API (authenticated, also accepts a URL token in `?token=`), so browsers never need direct access to Garage. The `compile_project` task (`jobs/tasks.py`) runs in the `compile` queue with `acks_late`: if a worker dies the message is redelivered, so tasks must be safe to re-run (it skips finished jobs). `updated_at` is the heartbeat; `reap_stale_jobs` fails jobs idle >10 min running / >30 min queued.

`jobs/compile.py` materialises the project (text from Postgres, binaries from S3) into a temp dir, runs engine → bibtex/biber (biber if `.aux` has `\abx@aux@` or the source uses biblatex) → 2 more passes, treats "a PDF exists" as success even if the engine exited non-zero, and always deletes the temp dir. Log output is capped at 200 KB.

**Tectonic** (v0.0.7): the `worker-tex` image carries a pinned tectonic release and its TeX Live 2022 package bundle, unpacked to a directory (`/opt/tectonic/{bin,bundle,cache}`, `TECTONIC_HOME`; built in the Dockerfile's own `tectonic` stage, both downloads checked against pinned SHA-256s; about 3 GB). It runs with `--untrusted --bundle <dir>`, so it never downloads (the compile worker has no egress in k8s), with a read-only format cache built at image build time. Differences from the other engines: it runs its own bibtex and rerun passes in one command; **biblatex/biber is not supported** (a document's `.run.xml` chooses biber's arguments, so tectonic's PATH holds only tectonic itself, and the bundle's biblatex would not match the image's biber anyway); `openin_any` does not apply (tectonic reads absolute paths, like lualatex, so the scrubbed environment and the non-dumpable worker are the protection); a package missing from the bundle fails with "<file> is not in the offline package bundle tectonic uses." as the job error. Images without it (the `api` image) report "tectonic not available".

**Source→PDF position (SyncTeX).** Every engine compiles with `-synctex=1` (latexmk via its `-pdflatex=` command). If the request carried `focus: {file, line}` (the editor sends the caret's line), `forward_search()` runs `synctex view` inside the same temp dir (while the paths in the SyncTeX data still exist) and returns `{page, x, y}` (PDF points from the page's top-left) as `result.focus`. It is best effort and never fails a compile: a malformed hint is dropped by the API, a blank/comment line falls back to the nearest line with output (±12), a file not part of the compile or a failed compile gives `null`, and a line past the end snaps to the last page. The SyncTeX file is untrusted input, so `synctex` runs through `run_command`.

New async features follow this pattern: model in `jobs`, task in `jobs/tasks.py`, route to a named queue in `CELERY_TASK_ROUTES`, status via `/api/jobs/:id`.

**AI endpoints (`apps/api/ai`).** `/api/llm`, `/api/agent/run`, `/api/vision/latex`, `/api/plot/from-table` create a `Job` and enqueue `ai.tasks.run_ai_job` on the `ai` queue. **With `async: true` in the body (a form field `async=true` for multipart) they answer `{ok, jobId, status}` at once** and `GET /api/jobs/:id` returns the endpoint's response body as `result` when the job ends (stored in `job.result['body']`, the endpoint's usual response shape); validation errors still answer directly. The frontend always does this through `runAiJob()` in `api/client.ts` (polls 1 s, 2 s after 30 s, 15 min cap; `onProgress` gets `progressLog` lines; an `AbortSignal` stops polling, `cancelJob` stops the worker). Without `async` (deprecated, for old clients) the view **blocks up to `AI_WAIT_SECONDS` (300) polling the DB**, holding a web thread; if the wait runs out the reply is `{ok: false, error, jobId}` and the job keeps running. `arxiv/search` and `arxiv/bibtex` are quick and run inline in the api. Keep these true when changing this code:
- **API keys never touch Postgres in plain text, `Job` rows or the Celery result backend.** The view splits `llmConfig` into public fields (`model`, `endpoint`, `profile`) and `{apiKey}`, resolves who pays (below), stores only the chosen endpoint and model in `Job.params`, and the key travels only as a task argument (briefly in the Redis broker; the task is `ignore_result`). `AiApiTests.assert_key_not_persisted` and `UserKeyTests.assert_no_secret_persisted` guard this.

A request without its own key uses the saved profile it names (`search`/`vision` fall back to `llm`), with that profile's own endpoint and model; MinerU transfers use the saved `mineru` token and base. Every change is a credential event (`user_llm`/`user_mineru`). - **Workspace provider** (`integrations/llmconfig.py`, `WorkspaceLlmConfig`, `GET/PUT/DELETE /api/workspaces/:id/llm`; owners/admins manage it, members only see that one exists). Resolution order for a request (`ai.usage.resolve()`, used by agent, vision, plot, `/api/llm` (the workspace only when the body has `projectId`) and transfer start (the target workspace)): the project's workspace provider (only for members with a write role; it replaces the browser's whole config, since endpoint, model and key belong together), else the request's `llmConfig` **if it carries a key** (API clients; the UI never sends one), else the user's saved key for the requested profile, else the worker's `OPENPRISM_LLM_*` defaults **as a whole**: the browser's endpoint and model are dropped, and `llm.resolve_config()` on the worker also never pairs its own key with a request's endpoint (otherwise anyone could have the operator's key sent to a server they name; MinerU's `resolve_config` does the same for `OPENPRISM_MINERU_TOKEN`).

Workspace providers: `GET /api/workspaces/:id/credential-events?before=&limit=` (owners/admins; others 403, non-members 404). A user's own (Zotero, later their AI keys; `owner`, deleted with the account): `GET /api/integrations/credential-events`. Admins see `usage: {today, last30Days}` in the GET and in the Settings block. Counts are jobs, not tokens. Per-minute limits come from `common/ratelimit.py` (`enforce(scope, user, n)`, Redis fixed window). The decrypted key travels exactly like a browser key (task argument / Redis job secret) and `Job.params['llmConfig']` keeps only endpoint and model. The key is stored encrypted with `CREDENTIAL_ENCRYPTION_KEY`; the endpoint passes the SSRF guard when saved and again on every call.
- **SSRF guard** (`ai/ssrf.py`): user-supplied LLM endpoints that resolve to private/loopback/link-local addresses are refused unless `LLM_ALLOW_PRIVATE_ENDPOINTS=1` (dev only, for local models; compose passes it to `worker-ai`). Patches stay proposals and may span files. Recorded-task tests: `ai/test_edit_tasks.py` (replayed model, real compile under `worker-tex`).

Edit requests are limited per user per minute (`AI_EDIT_RATE_PER_MINUTE`, default 20; 429 `{ok:false,error}`), counted in the Redis cache; the plain Assistant is not limited.

Recent requests: `localStorage` `openprism-ai-recent-v1` (20, Up/Down in an empty bar). Browser tests: `e2e/ai-command.spec.ts` (the job protocol stubbed at the network by `stubAiJob`, plus one test against the real API).

Unified diffs are built/applied by `ai/patches.py` (tolerates shifted hunks and stripped blank context lines).
- **Plot** (`ai/plot.py` + `plot_runner.py`) runs LLM-written Python in a subprocess: AST check (no imports/dunders/introspection) → whitelisted builtins → scrubbed environment → rlimits + timeout → temp dir deleted. This is defence in depth, **not a real sandbox** (e.g. `plt.sys.modules` is reachable). Real isolation must come from the deployment: `worker-ai` with no extra secrets, a pids limit, and a NetworkPolicy denying egress except LLM providers (the Helm chart does not ship one yet; see issues #111 and #112).
- Tests fake the LLM with a local HTTP server (`FakeLLM` in `ai/tests.py`) and run the task inline; real-Celery routing was verified manually with `docker compose up worker-ai`.

**Template transfer (`apps/api/transfer`).** Port of the LangGraph pipeline with the same endpoints and `{status, progressLog, error}` shape the frontend expects (`pending|running|waiting_images|success|failed`), but nothing blocks: `/start` creates the target project from the template and a `Job`; the **first `/step` claims the job and enqueues segment 1; later `/step` calls are read-only status polls**, as is `/status/:id`.
- **Hand-written state machine, not LangGraph** (`transfer/engine.py`; LangGraph's checkpointer would write the API key into Postgres). It runs nodes (`transfer/nodes.py`, one function per Node file) in *segments*: a segment ends at the pause before `checkLayout` (status `waiting_images`) or at `finalize`. `POST /submit-images` stores the screenshots in S3, bumps the segment number and enqueues the next segment. Only small state persists between segments (`engine.PERSISTED`: counters, compile/layout results, S3 keys); large intermediates (source, Markdown, plan) live in memory for one segment, so **a segment must be restartable from its entry point** (`start` or `checkLayout`). A stale or duplicate segment is ignored (segment number) and a Postgres advisory lock stops two workers running the same job.
- **Secrets** (LLM key, MinerU token) live in Redis under `openprism:job-secrets:<jobId>` with a TTL (`JOB_SECRET_TTL_SECONDS`, 6 h, refreshed on use) via `common/secrets.py`, and are deleted when the job ends, fails or is reaped. Never put them in `Job.params`/`result`/`progress_log`; `TransferApiTests.assert_no_secrets_in_db` guards this.
- Snapshots of files the pipeline overwrites go to S3 (`jobs/<id>/snapshots/…`), not the project tree. The final PDF is `jobs/<id>/output.pdf`, served by `GET /api/jobs/:id/pdf`.
- A worker crash fails the job (reaped after 10 idle minutes; a job left at `waiting_images` for `JOB_WAITING_STALE_MINUTES`, 60, is reaped too); there is no auto-resume because the key was never persisted. **A failed transfer deletes its target project** (`transfer/cleanup.discard_target`, called from the engine's fail/finish paths, the segment timeout and `reap_stale_jobs`): the job is detached first (Job.project cascades) and keeps its error, with `result.targetDeleted` (`targetDeleted` in the status response) and a progress line; the panel says the unfinished project was removed. Compile "success" means a PDF exists even if the engine exited non-zero, so `fixCompile` only fires when no PDF is produced.
- MinerU (`transfer/mineru.py`): the user-supplied `apiBase`, the upload URL and every redirect hop of the result download pass the SSRF guard; result-zip paths are validated strictly (unsafe path = error).
- **Layout check in the browser:** at `waiting_images` the job's `pdfKey` points at the PDF just compiled (`GET /api/jobs/:id/pdf`). `TransferPanel` renders its first 8 pages to JPEG with pdf.js (`app/pageImages.ts`), posts them to `/submit-images` and keeps polling; if rendering fails it posts an empty list (the server then skips the check) and shows a warning. The loop can pause up to `MAX_LAYOUT_LOOPS` times per job. Browser test: `e2e/transfer-layout-check.spec.ts` (transfer endpoints stubbed).

**arXiv import.** `GET /api/projects/import-arxiv-sse?arxivIdOrUrl=&projectName=&token=` creates an `import` Job (queue `import`, worker-ai) and relays its progress as SSE `progress`/`done`/`error` events (auth via an `import`-scoped URL token in `?token=`, since EventSource can't set headers). The task streams the download to a temp file, unpacks it with path/link/size checks (tar, or a single gzipped `.tex` saved as `main.tex`), and deletes the project if anything fails.

### Account lifecycle (`apps/api/accounts`)

- **Passwords** (`passwords.py`): `POST /api/auth/password/forgot` always answers `{ok:true}` (never reveals whether an account exists) and mails a `PasswordResetTokenGenerator` link (`/reset-password?uid=&token=`, single use, `PASSWORD_RESET_TIMEOUT` 1 h); `…/password/reset`, `…/password/change` (current password required, returns fresh tokens). Every password change revokes all the user's refresh tokens (`revoke_refresh_tokens`) and mails a notice. Frontend: `app/PasswordPages.tsx`, `app/AccountPage.tsx` (`/account`, from the account menu).
- **Email verification** (`verification.py`): registration mails a signed, timestamped link (`/verify-email?token=`, `TimestampSigner` over `<id>:<email>`, `EMAIL_VERIFY_MAX_AGE` 3 days); `POST /api/auth/verify-email` (public) sets `email_verified_at` and only then accepts pending `WorkspaceInvite`s for the address (never at registration: anyone can register any address); `…/verify-email/resend`. `REQUIRE_EMAIL_VERIFICATION=1`: `collab.auth.verified_enough` (inside `IsRealUser`/`IsUserOrGuest`) answers 403 for unverified accounts except views with `allow_unverified = True` (me, logout, resend, change password), the collab websocket refuses them, and the UI shows only `VerifyGate`. `REGISTRATION_MODE=invite`: registration needs an invitation, see *Sign-up gate* below. `/api/auth/me` reports `emailVerified` and `verificationRequired`. Accounts that existed before migration 0002 are marked verified. Mail is sent inline under tests (`MAIL_SEND_INLINE`). The browser test helper `signIn()` hides the unverified reminder banner unless asked (`{ verifyBanner: true }`).
- **Invitation mail** (`projects/workspaces.py`): inviting an existing account still adds it at once and mails `workspace_added`; an address without an account gets a `WorkspaceInvite` and `workspace_invite` with `/register?email=…&invited=1` (the register form pre-fills it). `POST /api/workspaces/:id/members/invite-<email>/resend` (admins, once per 10 min, else 429). `accounts.tasks.send_email(..., invite_id)` sets `WorkspaceInvite.send_failed` after the last retry fails (cleared by a later success); the Members list shows sent time, "Email not sent" and Resend. Workspaces reload when `account.emailVerified` changes, so invitations accepted by verifying appear at once.
- **Platform invitations** (v0.1.2, `invitations.py`, `PlatformInvite`): a superadmin's invitation for one address to register, optionally into a workspace with a role. Only the SHA-256 of the token (`pi1.<random>`) is stored; the raw token exists in the mailed link (`/register?invite=…&email=…`, template `platform_invite`) and the return values of `create()`/`resend()`. `PLATFORM_INVITE_DAYS` (7). One live invitation per address: `create()` revokes earlier unused ones and `resend()` rotates the token and expiry. `find_valid(email, token)` is the only check (wrong, expired, revoked, used and other-address all give `None`); `status()` = `sent|mail_failed|used|expired|revoked`. Existing accounts cannot be invited. Mail outcome is recorded in `send_failed` through `send_template(..., platform_invite_id=)`.
- **Sign-up gate** (v0.1.2, `signup.py`): `check_signup(email, invite_token)` is the one place that decides whether an address may register, and every sign-up path must call it (the allauth adapters' `is_open_for_signup` too, backlog B). `open`: anyone. `invite`: a valid platform invitation for that address (`RegisterSerializer`'s optional `invite`), or a `WorkspaceInvite` unless `WORKSPACE_INVITES_ALLOW_SIGNUP=0`. Everything else gets one message (`REFUSED`), and the gate runs before the "account exists" check, so nothing reveals who is invited or registered; attempts are limited to 10 per 15 minutes per address and per token (429). Registering with a platform invitation locks and uses the invitation in the same transaction as the account (two requests with one link cannot both win; a failure rolls back and leaves it usable), marks the address verified (no verification mail), accepts waiting workspace invitations and joins the invited workspace and role if it still exists. Tests: `accounts/test_signup.py`.
- **Closed sign-up pages** (v0.1.2): the public `GET /api/config` (`common/views.py`, cacheable 60 s) returns `{registration: open|invite, contactEmail}` (`REGISTRATION_MODE`, `ACCESS_CONTACT_EMAIL`) and nothing else; the frontend reads it once (`fetchPublicConfig()`). In invite mode the landing page offers Sign in and the contact address, the sign-in form drops "Create an account", and `/register` shows `ClosedSignup` (design/AuthScreen.tsx) unless the link carries `?invite=<token>` (platform invitation: the form opens with the mailed address fixed and sends the token) or `?invited=1` (workspace invitation). Open mode is unchanged, but a valid `invite` link there also verifies the address. Browser tests `e2e/invitation-only.spec.ts` (closed mode simulated by stubbing `/api/config`; the compose stack runs open).
- **allauth as a library** (v0.1.3, `docs/spike-allauth.md`): `django-allauth[mfa]` is installed for its second-factor code (and later passkeys and social sign-in) with `AccountMiddleware` but **no allauth URLs, views or sessions**; our JWT + cookie session is untouched. Its secrets are encrypted by `accounts/mfa_adapter.py` (our Fernet key). `accounts/emails.py` keeps one primary `EmailAddress` per account in step with `User.email`/`email_verified_at` through a `post_save` signal (a bulk `QuerySet.update` sends none: call `emails.sync(user)`). `Authenticator` and `EmailAddress` are unregistered from the admin. **API tests ignore `REGISTRATION_MODE`, `AUTH_RATE_LIMIT` and `AUTH_REFRESH_RATE_LIMIT` from the environment** (registration is open, limits are 10000/min under the test runner; a test that needs invite mode uses `override_settings`), so `docker compose run --rm api python manage.py test` needs no extra `-e` flags even when `.env` sets invite mode (#105). The browser tests are different: they need the running stack to allow registration, so for `npm run e2e` start the api with `REGISTRATION_MODE=open AUTH_RATE_LIMIT=10000/min docker compose up -d api`.
- **Two-factor sign-in** (v0.1.3, `mfa.py`): TOTP (allauth's code; accepts one period either side, each code once, replay guard in the Redis cache) plus 10 recovery codes (shown once). `/api/auth/login` for an account with a factor answers `{mfaRequired, ticket}` and issues **no access token and no refresh cookie**; `POST /api/auth/login/mfa {ticket, code}` (ticket: signed, 5 min, works once, 5 wrong codes then dead; 10 wrong codes per account per 15 min then 429) issues them. A refresh token only exists after complete sign-in, and enabling or disabling revokes every earlier one (this browser gets fresh tokens), so `/refresh` cannot skip the step. Endpoints (signed-in, `allow_unverified`): `GET /api/auth/mfa`, `POST …/mfa/totp/setup {password}` (secret, otpauth URI, server-made QR SVG and a signed 10-minute setup token that carries the secret: nothing is stored yet), `…/totp/enable {setup, code}` (returns the recovery codes), `…/recovery-codes {password, code}`, `…/disable {password, code}`; both change mails (`mfa_enabled`, `mfa_disabled`). `/api/auth/me` reports `mfaEnabled`. Tests: `accounts/test_mfa.py`, `e2e/two-factor.spec.ts` (computes TOTP codes from the displayed key). UI: `AuthScreen` has a code step (`onSubmit` resolving `'code'`, then `onSubmitCode`; the ticket lives in `LoginPage` state only), `AccountPage` has the *Two-factor authentication* block; `api/client.ts` `login()` returns `{mfaTicket}` instead of an account when a code is owed.
- **Passkeys** (v0.1.4, `passkeys.py`, `softkey.py` = a software authenticator for tests): WebAuthn credentials stored as allauth `Authenticator` rows (type webauthn), always registered with user verification and a discoverable credential, so a passkey sign-in needs no username and counts as both factors (it skips the TOTP step). fido2 is driven directly because allauth keeps the ceremony state in a Django session; ours is in the cache under a random id, single use, 5 min, bound to the registering user. `PASSKEY_RP_ID` (default: host of `APP_BASE_URL`; changing the host invalidates every passkey); origins checked against `APP_BASE_URL` + `TRUSTED_ORIGINS`. Endpoints: `POST /api/auth/passkeys/options {password}` → `{options, state}`, `POST|GET /api/auth/passkeys`, `PATCH|DELETE /api/auth/passkeys/:id` (delete needs the password and signs other browsers out), public `POST …/passkeys/login/options` and `…/passkeys/login {state, credential}`. `mfa.remove()` only removes TOTP and recovery codes, never passkeys. Tests `accounts/test_passkeys.py`, `e2e/passkeys.spec.ts` (Chromium's CDP virtual authenticator). UI: `api/client.ts` converts the JSON mapping to and from ArrayBuffers (`addPasskey`, `loginWithPasskey`; a cancelled prompt becomes a calm message), `AuthScreen` has *Sign in with a passkey* (`onPasskey`, hidden without `PublicKeyCredential`), `AccountPage` has the *Passkeys* block.
- **Social sign-in** (v0.1.4, `social.py`, `socialviews.py`, `LinkedIdentity`, `fake_oidc.py`): Google and ORCID through our own OpenID Connect client (code + PKCE + nonce; the id_token is verified with PyJWT against the provider's JWKS), no sessions. A provider is on when `SOCIAL_GOOGLE_CLIENT_ID/_SECRET` / `SOCIAL_ORCID_CLIENT_ID/_SECRET` are set (`ORCID_SANDBOX=1`; `SOCIAL_<P>_AUTH_URL/_TOKEN_URL/_JWKS_URL/_ISSUER` override endpoints for the fake provider); redirect URI `APP_BASE_URL/api/auth/social/<provider>/callback`; `/api/config` lists `socialProviders`. Browser navigation endpoints answer redirects: `GET /api/auth/social/<p>/start?intent=login|link&ticket=&next=` (linking needs a one-time ticket from `POST …/<p>/link-ticket {password}`, because a navigation carries no bearer token), `GET …/<p>/callback`. Success sets the refresh cookie and redirects to `next` (the SPA refreshes on load); an account with TOTP is redirected to `/login?mfa=<ticket>&next=` (no cookie); failures go to `/login?error=<denied|expired|failed|not_invited|verify_first|no_email|linked_elsewhere|unavailable>`. Rules: a provider email counts only when `email_verified`; an unknown identity links by email only to an account whose own address is verified (else `verify_first`); an identity with no account is a sign-up through `signup.check_signup(email, None, address_verified=True)` (a live platform invitation for the proved address counts without its token, `invitations.find_for_address`), creating a verified account with an unusable password; ORCID usually has no email, so only linked ORCID identities sign in. `GET /api/auth/social`, `DELETE /api/auth/social/:id` (password unless none; `methods.others_remain` refuses the last way in, which also guards passkey removal). - **Sign-in methods** (v0.1.4, `methods.py`, `signins.py`): `methods.others_remain()` refuses removing the last way to sign in (a usable password, a passkey or a linked identity). Accounts created by a provider have an unusable password (`hasPassword: false` in `/api/auth/me`): wherever a password re-confirms a change (`methods.confirm`, used by `mfa.require_password`, email change, account deletion, linking) they type their own **email address** instead, and `POST /api/auth/password/change` needs no current password for them (*Set a password*). Every successful sign-in (password, password+code, passkey, google, orcid; not the password step alone) writes a `SignInEvent` with the address cut to its network (IPv4 /24, IPv6 /48) and the user agent; `GET /api/auth/sign-ins` returns the account's own newest 20; the beat task `accounts.tasks.prune_sign_ins` deletes after `SIGNIN_KEEP_DAYS` (90). - **Changing the email address** (v0.1.3, `emailchange.py`): `POST /api/auth/email/change {email, password}` holds the new address as an unverified allauth row and mails a signed link (`/confirm-email?token=`, 1 h, names the old and new address) to it and a notice to the old one; `POST …/email/confirm {token}` (public) swaps `User.email`, marks it verified (accepting waiting workspace invitations), deletes the other address rows, revokes every refresh token and mails the old address. `GET|DELETE /api/auth/email` show/cancel the pending change. Account page *Email address* block; tests `accounts/test_emailchange.py`, `e2e/email-change.spec.ts`.
- **Deleting an account** (`deletion.py`, `DELETE /api/auth/me {password}`): deletes the personal workspace and team workspaces where the user is the only member, with their projects (rows first in one transaction, then storage prefixes), memberships, tokens and the Zotero key. Refused (409 `{workspaces}`) for team workspaces the user alone owns while others remain. An owner can make another member an owner (`PATCH …/members/:id {role: owner}`, owners only, members only; owners cannot be demoted), so workspaces can have several owners.

### Django admin (`apps/api/accounts/adminsite.py`, v0.1.1)

The back end at `/admin/` is for **superadmins only**: `accounts.adminconfig.SuperuserAdminConfig` (in `INSTALLED_APPS` instead of `django.contrib.admin`) makes `SuperuserAdminSite` the default site, whose `has_permission` and login form need an active `is_superuser` (`is_staff` alone, or model permissions, open nothing; a staff user gets the same "correct email and password" error as a wrong password). It is the only user of Django sessions: cookie `openprism_admin` (httpOnly, `SameSite=Strict`, `Secure` by the refresh cookie's rule, `ADMIN_SESSION_HOURS`), CSRF cookie likewise, `CSRF_TRUSTED_ORIGINS` = `TRUSTED_ORIGINS`. The app's API ignores sessions (no `SessionAuthentication`), so an admin session opens nothing in `/api/`. The login form is limited per client address (`ADMIN_LOGIN_RATE_PER_15_MIN`, `common.ratelimit.hit(..., window_seconds=900)`, the address resolved like the API's throttles with `TRUSTED_PROXY_COUNT`; 429 with `Retry-After`). ### Zotero (`apps/api/integrations`, `app/ZoteroPanel.tsx`)

A user connects their Zotero account with an API key (`PUT /api/integrations/zotero`); the key is verified against Zotero, then **stored encrypted** (`crypto.py`, Fernet via `CREDENTIAL_ENCRYPTION_KEY`) in `ZoteroConnection`. It is never returned by any endpoint (status shows the username and last four characters), never logged, and only `zotero.get_zotero_key()` decrypts it. Real accounts only: guests are refused by the default permission.
- **Client** (`zotero.py`): fixed host `ZOTERO_API_BASE`, `Zotero-API-Version: 3`. `Backoff`/`Retry-After` are honoured with a bounded wait (`MAX_WAIT`, 5 s); longer asks become a "try again in N s" error instead of parking a web thread. A 403 means "reconnect Zotero". A `library` is `user` or a numeric group id checked against the user's groups; collection and item keys must be alphanumeric, so nothing user-supplied reaches another Zotero path.
- **Browse** (`GET /api/integrations/zotero/{libraries,collections,items}`) returns top-level items only, 50 per page at most.
- **Add to the bibliography** (`POST /api/projects/:id/zotero/add {library, keys, bibFile?}`, write access): items are rendered one by one (`include=bibtex` or `biblatex`, chosen by whether any `.tex` loads biblatex) and **appended** under a `% zotero: <library>:<itemKey>` comment, so re-adding is recognised (reported as `skipped` with the entry's current cite key) and nothing already in the file is rewritten. Cite keys are Zotero's own; if one is unusable or already taken by a different entry a `lastname+year+word` key is generated. `bibtex.parse_single_entry` accepts only one regular entry (no `@preamble/@string/@comment`, balanced braces, size limit, no control characters): the file is fed to bibtex/biber in the compile worker. The bib file is `bibFile`, else the project's only `.bib`, else `references.bib`.
- **Live rooms:** this predates v0.0.9, when a REST write to an open file was overwritten by the next live save (it no longer is, see *External writes* under collaboration): when `collab.views.live_room()` is true the server does not write; it returns `applied: false` and the entry `text`, and the editor appends it through the live document (`onAppendLive`; it can only do so for the file it has open, otherwise it asks the user to open it). `flush_room()` runs first so the duplicate check sees current text.
- **Testing without a Zotero account:** unit tests use `common.testing.FakeZotero`. For the browser test and manual QA run `ZOTERO_API_BASE=http://localhost:9099 docker compose up -d api` and `docker compose exec -d api python -m integrations.devserver 9099` (any API key is accepted), then `E2E_ZOTERO=1 npm run e2e -- zotero`. Restart the api without the override afterwards.

### Version history (`apps/api/versions`)

Every **compile that ran** saves a `ProjectVersion`: a manifest of the project's files (`path, kind text|binary|dir, size, sha256`) plus the PDF at `versions/<projectId>/<versionId>.pdf` and the job's capped log at `…/<versionId>.log` (`log_key`). A compile without a PDF is kept too, as `status: failed` with no PDF (v0.0.4.1: "what broke it"); `GET …/versions/:vid/log` returns the log and `/pdf` of a failed version is 404. A compile refused before the files were materialised, a timeout or a crash saves nothing, nor do the transfer pipeline's internal compiles (they call `jobs.compile` directly, not the task).
- **The snapshot is what the compiler saw.** `jobs.compile.materialise()` returns the entries it wrote and `compile_project` hands them back as `snapshot`; `jobs.tasks.save_version` records that list (never a second read, and never the on-disk copies, which a hostile document can rewrite). A snapshot failure is logged and the compile still succeeds without `versionId`.
- **Storage:** file contents are stored once per project by hash in `VersionBlob` (text in Postgres, binaries copied server-side to `versions/<projectId>/blobs/<sha256>`; project binary keys are immutable, so the copy has the hashed bytes). A compile whose manifest hash, main file, engine and status equal the latest version's creates nothing and reports that version (`versionCreated: false`). Numbers are per project and allocated under a lock on the project row. `files.delete_project_files` also removes the `versions/<id>/` prefix.
- **Read API** (`versions/views.py`, any member and invite guests, non-members 404): `GET /api/projects/:id/versions[?limit&before]`, `…/versions/:vid` (with manifest), `…/versions/:vid/pdf` and `…/versions/:vid/file?path=` (both also take a URL token in `?token=`; text comes back as JSON, binaries sandboxed like `/blob`), `…/versions/diff?from=<vid>&to=<vid|current>[&all=1]` (per-path `added|removed|modified|unchanged` from manifest hashes; the UI fetches both file versions and diffs text itself). Against `current`, binaries have no stored hash, so equal-size ones are hashed on demand.
- **Naming and retention** (`versions/retention.py`, `versions/tasks.py`): `PATCH …/versions/:vid {name}` names (max 100 chars) or clears a name and `DELETE …/versions/:vid` removes one; both need write access (guests only with an editor invite). A named version is pinned: it cannot be deleted until unnamed and retention never touches it. The beat task `versions.tasks.prune_versions` (daily, queue `import`) keeps the newest `VERSION_KEEP_UNNAMED` (50) unnamed successful versions and, separately so failures never push good versions out, the newest `VERSION_KEEP_FAILED` (10) unnamed failed ones per project, and deletes the rest; delete and prune share `delete_versions()`, which then removes blobs no remaining version references (`collect_blobs`, idempotent). A PDF key still used by another version is kept; logs are never shared (a restore copies its own).
- **Storage report and time-based retention** (v0.0.4.1, `versions/storage_report.py`): `GET /api/workspaces/:id/storage` (owners/admins; others 403, non-members 404) returns per-project `fileBytes` (text as UTF-8 bytes + binary sizes), `versionBytes` (the project's blobs + each distinct PDF key once + logs, `log_size`) and `versionCount`, from aggregate queries only (no S3 listing; trashed projects included). `PATCH` the same URL with `{versionRetentionDays: 1–3650 | null}` sets `Workspace.version_retention_days`: the nightly prune then also deletes unnamed versions older than that, always keeping each project's newest version. It is a report, not a quota. UI: the *Storage* block in workspace Settings (`app/WorkspaceStorageBlock.tsx`, admins only).
- **Restore** (`POST …/versions/:vid/restore`, write access): makes the project's files exactly the version's and records a new version (same manifest, `restored_from`, its own copy of the PDF), so history is never rewritten; an identical project is a no-op (`restored: false`). The changes are applied by `projects.files.apply_changes` as one unit: binaries are copied into new random keys first, rows change in one transaction, replaced objects are deleted `on_commit`, and any failure (including recording the version) leaves the project untouched and the staged keys removed. **Live rooms** (designed before v0.0.9's *External writes*, which would now carry the text writes into open rooms): the view first `flush_room()`s every text file, evicts rooms nobody is connected to (`collab.views.evict_idle_room`: a new `KIND_EVICT` control message; an idle room otherwise lingers `COLLAB_ROOM_EVICT_SECONDS` and would keep serving its old text), recomputes the diff, and answers **409 `{files: […]}` with nothing written** if a room with connected clients still holds a file the restore would change. The editor must leave its own rooms before calling.
- **Single-file restore** (`POST …/versions/:vid/restore-file {path}`, write access, v0.0.4.1): puts one file of the version back (text or binary, also one deleted since) through `apply_changes`, touching nothing else and **recording no version** (the next compile does). Live rooms as for a whole restore, but only for that path (409 `{files:[path]}`); a file that already matches is `restored: false`. In the Compare dialog against *Current project*, a changed or removed file offers **Restore this file** (`EditorPage.restoreFileInEditor` leaves this tab's room only when that file is the open one).
- Compile job results carry `versionId`, `versionNumber`, `versionCreated`.
- **Editor UI** (`app/VersionsPanel.tsx`, right-rail tool *Versions*): lists versions (a failed one with a *Failed* badge and **Open log** instead of Open PDF; the log dialog lists errors with `app/compileLog.ts`, the parser the editor's log panel uses) (`canWrite` from the list response hides name/delete for viewers), opens an old PDF in the preview, names/unnames and deletes. Viewing an old PDF swaps the editor's `pdfUrl` for a blob URL (`versionView` keeps the build to return to), so outline, download and zoom keep working; the banner is derived from `pdfUrl === versionView.url`, so any other change of the preview (a compile, another file's build) ends the view. **Compare** (`VersionCompareModal.tsx`): pickers for any two versions or the current project, the server's manifest diff for the file list, and text diffs built in the browser with `SplitDiff.tsx` (`buildSplitDiff`/`SplitDiffView`, shared with the AI patch preview; each row is drawn in both columns, so tests read removed lines from the left column and added ones from the right). A **Files | PDF** switch (v0.0.4.1) shows `PdfCompareView.tsx`: both PDFs (a version's, or the preview's current build for *Current project*) rendered with pdf.js in the browser and diffed per page by pixels (`app/pdfCompare.ts`, `diffPages` is pure; at most 200 pages; a size mismatch or a page on one side only counts as changed), side by side or as a highlight of the changed pixels in the `--danger` colour, with a page strip and previous/next change. Failed versions and a tab with no build show a message instead. **Restore** (`EditorPage.restoreVersionInEditor`): the tab flushes and leaves its own live room (`setCollabEnabled(false)`, then waits ~0.5 s for the socket close), calls the restore API, bypasses the editor's in-memory file cache (`openFile(path, fresh)`, `refreshTree(keep, fresh)`), and rejoins; a 409 comes back as a result (not a throw) and the dialog lists the files and offers "Try again". Browser tests: `e2e/versions.spec.ts` (including a second, guest, browser holding the file open).

### Comments (`apps/api/comments`)

`CommentThread` (project, file `path`, `quote` + up to 32 characters of `prefix`/`suffix` context, the offsets it had, resolved flag) and `Comment` (author account or invite guest by `guest_invite_id`, `author_name` kept after account deletion, body ≤ 5000). **Anchors** (`anchor.py`): offsets are only a hint; `locate()` keeps them if the quote is still there, else scores every occurrence of the quote by surrounding context (ties: nearest the old position), else the thread is `orphaned` (listed, not drawn). The editor runs the same algorithm on its live text (`app/commentAnchor.ts`). **Endpoints:** `GET/POST /api/projects/:id/comments[?path=]` (list includes `canComment`/`canModerate` and current anchors computed against the stored text), `PATCH/DELETE …/comments/:tid` (resolve/reopen; delete by its starter or a write role), `POST …/:tid/replies`, `PATCH/DELETE …/:tid/replies/:cid` (own comments; write roles may delete any; deleting the last comment deletes the thread). **Who:** `Membership.COMMENT_ROLES` (write roles + commenter) and invite links with role `editor` or `commenter` (a new link role: read + comment) may comment, reply and resolve; viewers and viewer links read. Guest-reachable (`IsUserOrGuest`). `files.rename` moves threads with their file; `files.delete` removes them.

**Editor side** (`app/CommentsPanel.tsx`, `app/commentMarks.ts`, `app/commentAnchor.ts`): right-rail tool *Comments*; select text and press **Comment** (toolbar, Ctrl/Cmd+Alt+M) to start a thread. `EditorPage` loads all threads (on open, on file change, every 15 s while the panel is open), places the open file's unresolved threads against the live text ~300 ms after typing stops and draws them as `.cm-comment-range` marks (a StateField that maps them through edits in between); clicking one opens its thread. The panel shows this file or the whole project, collapses resolved threads, and lists orphaned ones with "Text no longer found". Commenters and viewers get a read-only editor; Comment controls follow `canComment` from the list response. Browser tests: `e2e/comments.spec.ts` (two browsers).

### Real-time collaboration (`apps/api/collab`)

Wire-compatible with the browser's `CollabProvider` (`apps/frontend/src/collab/provider.ts`; standard y-websocket framing: type 0 = sync, 1 = awareness; one `Y.Text` named `content`) at `ws(s)://…/api/collab?projectId=&file=&token=`. Built on **`pycrdt`** (Yrs bindings) + a Channels `AsyncWebsocketConsumer`; `pycrdt-websocket` was *not* used because we need our own auth, read-only enforcement and cross-replica fan-out. Gotcha: every `pycrdt` message helper (`create_sync_message`, `create_update_message`, `handle_sync_message`'s reply, …) already includes the outer message-type byte; don't prefix it again.
- **Rooms** (`rooms.py`): one `Room` per open file per process (`RoomManager`), holding a `pycrdt.Doc`, awareness, and the local connections (each with an outbox queue so Yjs callbacks never block). A room is evicted `COLLAB_ROOM_EVICT_SECONDS` (60) after its last client leaves, after a final flush.
- **Durable state** (`models.CollabDoc`, `store.py`): rooms load the Yjs *state*, not the file text, so every replica starts from the same CRDT history. Seeding from file text happens once, under a Postgres advisory lock (two replicas seeding independently would duplicate content on merge). On load, text that changed outside collaboration (REST edit, template apply…) is diffed in as a normal edit: **the file wins when a room starts**. A flush merges (never overwrites) with the stored state and writes the text into `ProjectFile` in one transaction; it runs `OPENPRISM_COLLAB_FLUSH_DEBOUNCE_MS` (800) after edits and every `COLLAB_SYNC_INTERVAL_SECONDS` (30) as anti-entropy.
- **External writes** (v0.0.9, #54): every text write in `projects/files.py` other than a room's own flush (`write_text(..., sync_live=False)`), i.e. REST saves, uploads, template apply/convert, transfer, `apply_changes`, calls `store.external_write()` inside its transaction *before* touching the file row (advisory lock, then row: the same order as a flush). If the file has a `CollabDoc`, its text is rewritten to the new content with `diff_replace` and the state saved; after commit the delta is published on the room channel as a `KIND_UPDATE`, so open editors on every replica get it as a normal concurrent edit (typing elsewhere in the file survives). A lost message heals at the room's next flush, since the stored state already has the edit. Files never opened live have no `CollabDoc` and are untouched. Tests: `collab.tests.LiveWriteTests`; browser: `e2e/collab-live.spec.ts`.
- **Renamed or deleted files** (v0.0.9, #55): a room keeps the id of the `CollabDoc` it loaded, and `store.flush(project, path, doc_id, update)` finds the row by that id: gone (file or project deleted) → `GONE`, nothing written; moved (`files.rename` moves the rows with the files) → `MOVED`, merged into it and written at the new path, so the last edits survive a rename. Either way the room sends its clients a text frame `{"type":"closed","reason":"renamed"|"deleted","path","to"}`, closes them with **4404** and leaves without another flush. `files.delete`/`rename`/`apply_changes` take the affected rooms' advisory locks before touching file rows (`store.lock_paths`, sorted; a flush takes its lock and then the file row) and publish `KIND_CLOSE` on each room's channel after commit, which makes the rooms flush now; the flush check is the safety net when the message is lost. The provider never reconnects after 4404 and calls `onClosed`; the editor opens the file under its new name or, if deleted, says so and opens the main file. Tests: `collab.tests.FileGoneTests`, `e2e/collab-live.spec.ts`.
- **Multiple replicas** (`coord.py`): edits, awareness and catch-up requests go over Redis pub/sub on the stored document's channel (`collab:doc:<CollabDoc id>`, so a room left over for a deleted file never exchanges edits with a new file at the same path); control messages (flush, evict, close) on the path's channel (`collab:room:<sha1>`); all tagged with the sender's instance id. Pub/sub is fire-and-forget, so a replica that opens a room publishes its state vector and replicas already holding it answer with the missing update plus their cursors (otherwise a late replica misses edits still unflushed in another process). Lost messages heal at the next flush/merge. Replica liveness is a Redis zset (`collab:holders:*`), so `POST …/collab/flush` publishes a flush request and waits (≤5 s) for an ack from every live holder; the editor's Save in collab mode and anything that reads the file right after use this. `GET …/collab/status` reports connections and last flush error across replicas.
- **Auth** (`consumers.authorize`, `auth.py`, `tokens.py`): the websocket accepts `?token=` only as a **URL token** with `project` scope for that project (minted by the client before every (re)connect); what the connection may do comes from the membership or invite as they are at connect time. Raw invite tokens and access tokens in the URL are refused. There is no localhost bypass. Invite tokens are `op2.<random>`, only their SHA-256 is stored (`CollabInvite`), default 24 h (max 7 d), role `editor` or `viewer`. `POST /api/projects/:id/collab/invite {role?}` needs write access; `POST /api/collab/resolve {token}` is public (a POST so the invite token is never in an API URL). **Viewers are read-only server-side**: their sync step-2/update frames are dropped (they still receive content and show cursors). Rejections are real close codes sent after accept (1008 unauthorised/not found/invalid path, 1003 binary file; 4404 later, when the file is renamed or deleted).
- **Managing links** (`collab/views.py`, `app/InviteLinks.tsx`): the Collaboration panel creates a link with a role (`editor`/`viewer`) and lifetime (1/3/7 days); `GET /api/projects/:id/collab/invites` lists unexpired links (never tokens) and `DELETE …/collab/invites/:inviteId` revokes one (write access, real accounts only). Revoking publishes `KIND_REVOKE` on the project channel (`coord.project_channel`; every room subscribes to it as well as its own), and each replica closes the connections whose `Conn.invite_id` matches with 1008. The editor is read-only (CodeMirror `readOnly`/`editable` compartment) whenever the tree's `canWrite` is false.
- **Guests:** the same invite token is the REST credential for people without an account (`Authorization: Bearer op2…`; for blob/PDF URLs they mint URL tokens like accounts do). `InviteAuthentication` yields a `GuestUser` confined to one project. The default permission is `IsRealUser` (guests refused everywhere); project-scoped views opt in with `@permission_classes([IsUserOrGuest])` (tree/file/blob/upload/files/folder/rename/file-order, compile, job status/pdf, collab flush/status), and `get_project()`/`get_job()` enforce the project and write role. Guests cannot list/create projects, call AI endpoints, or administer the project. **Any new project-scoped view that guests should reach needs that opt-in; anything else is automatically refused.**
- **Async DB access** goes through `collab/dbasync.py` (`thread_sensitive=False`, thread pool). `channels.db.database_sync_to_async` runs *all* calls of a process in one thread, so one slow flush would stall every room. Tests set `CONN_MAX_AGE=0` so pool-thread connections don't block `DROP DATABASE`.
- **Crashes** (v0.0.9, #56): every edit a replica receives from its own clients is also appended to its own Redis list for the document (`collab:log:<CollabDoc id>:<replica>`, listed in `collab:logs:<id>` and `collab:logged`, 1-day TTL); a flush reads the list's length before taking its snapshot and trims that many entries after saving, and only ever its own list. A room that starts replays every log of its document (updates are idempotent), and the beat task `collab.tasks.recover_update_logs` (every minute) saves the logs of replicas with no heartbeat in `collab:instances` for 90 s into the database (`store.flush`, from the stored state) and deletes them, so a crash between flushes loses nothing even if nobody reopens the file. Rooms drop cursors not renewed for `COLLAB_AWARENESS_TIMEOUT_SECONDS` (30; browsers renew every 15 s) and broadcast the removal, so a dead replica's cursors disappear. Tests: `collab.tests.CrashTests`. **Tests use Redis database 15** (`TEST_REDIS_URL` overrides; settings switch under `TESTING`), and the collab tests empty it in `setUp`.
- **Known limitations:** an edit a client sent but the dying replica had not yet appended to Redis (microseconds) is still lost if that client also goes away before reconnecting; a client that stays open re-sends it on reconnect anyway.
- **Verifying against the real client stack:** `node apps/api/collab/interop/yjs_client.mjs <baseUrl> <inviteToken> <projectId> main.tex [<secondReplicaBaseUrl>]` (it exchanges the invite token for a URL token first) drives the genuine `yjs`/`y-protocols` libraries against a running stack; with a second URL (e.g. `docker compose run -d --no-deps -p 8001:8000 api uvicorn config.asgi:application --host 0.0.0.0 --port 8000`) it exercises two processes over Redis. Unit tests: `docker compose run --rm api python manage.py test collab --noinput` (uses `channels.testing.WebsocketCommunicator`; `daphne`, in `requirements-dev.txt`, is installed only because `channels.testing` imports it).

### Running untrusted code safely (compile and plot workers)

Anyone who can edit a project (including an invite-link guest) controls the LaTeX that `worker-tex` compiles, and an LLM writes the Python that `worker-ai` runs for plots. These rules keep that safe; each is covered by a test that fails on the old code (`jobs/tests.py` `HostileDocumentTests`, `ScrubbedEnvironmentTests`; `ai/tests.py`):
- **Child processes get an allow-listed environment, never a copy of the worker's.** `jobs.compile.run_command` *requires* an explicit `env`; `_tex_env()` builds it (PATH/locale only, `HOME` = the per-compile temp dir, `shell_escape=f`, `openout_any=p`, `openin_any=p`). The worker's environment holds the database and storage credentials, and a document can print anything its process can read (including `/proc/self/environ`).
- **Worker processes are non-dumpable** (`config/hardening.py`, applied on `worker_init`/`worker_process_init` in `config/celery.py`), so the kernel refuses children access to `/proc/<ppid>/environ` and memory. This protects against LuaTeX's Lua `io.open` (unrestrictable: `--safer` breaks luaotfload) and `plt.sys.modules['builtins'].open(...)` in plot code. Don't put credentials in *files* the worker's user can read, for the same reason.
- `openin_any=p` applies to every engine **except `lualatex`** (luaotfload cannot run in paranoid mode). `latexmk` runs with `-norc` (a project `latexmkrc` is Perl code: this was a remote-code-execution hole) and `biber` with `--noconf`.
- Any new subprocess running user-influenced code must scrub its environment, run from a temp dir, bound its time/memory/file size, and have a test that a hostile input cannot read credentials.

### Frontend (`apps/frontend/src`)

**Layout.** React Router app (`app/App.tsx`) with routes for landing, project list / workspace home (`app/ProjectPage.tsx`, sections via `?section=`), the editor, and a collab-invite-join page. The editor (`app/EditorPage.tsx`, styles in `app/editor-shell.css`) is icon rails + collapsible/resizable side panels around an editor/PDF split: left = Files / Outline / project Search; right = Assistant / Review / arXiv / Websearch / Vision / Plot / Collaborate; the centre has an Editor / Split / PDF switch. Layout state persists in `localStorage` (`openprism-editor-layout-v1`). `app/TransferPanel.tsx` drives Template Transfer by polling `transferStep()` and handling `waiting_images`. All backend communication goes through `api/client.ts` (which also defines the shared request/response types; there is no separate `types/` module) and, underneath it, `api/auth.ts`. In dev, Vite proxies `/api` (incl. the WebSocket upgrade) to `OPENPRISM_API_URL` (default `http://localhost:8000`) and `/texlive` to SwiftLaTeX's cloud TexLive resources; in production nginx proxies `/api`.

**Accounts, sessions and workspaces.** In order of dependency:
- `api/auth.ts` (framework-free) owns credentials. An *account session* is the httpOnly refresh cookie plus an access token **in this module's memory only** (v0.0.8; `accounts/cookies.py` on the server): login, register and password change set the cookie and return only `access`; `POST /api/auth/refresh` with the cookie needs the header `X-OpenPrism-Refresh: 1` and, when the browser sends an Origin, a trusted one (403 otherwise), rotates the cookie and returns `access`; a body `refresh` still works for API clients (answered in the body), and with the header it moves an older build's stored token into the cookie. Logout revokes the cookie's token and deletes it. API requests stay `Authorization: Bearer <access>`, so only refresh/logout are cookie-authenticated. `initSession()` (awaited by `AuthProvider`, which stays `loading` meanwhile) refreshes once on load. Tabs coordinate because the server rotates the cookie on every use: refreshes take turns under the Web Lock `openprism-refresh`, and new access tokens and sign-outs go to the other tabs over the BroadcastChannel `openprism-auth` (a tab that waited for the lock and already got a fresh token skips its own refresh). A *guest* credential is an invite token in sessionStorage (this tab only) and **wins while present**. `apiFetch()` adds the language header and the right bearer token, and on a 401 refreshes once (single-flight) and retries; a rejected refresh signs the account out in every tab. A timer refreshes the access token a minute before it expires so long-lived websockets keep a valid token. Browser tests: `e2e/session.spec.ts`; the e2e `signIn()` helper gets the cookie through the context's own request client (a second context for the same account signs in again, since cookies rotate). For anything that cannot send headers (`<img>`, `<object>`, `EventSource`, websockets) use the URL-token cache in `api/auth.ts`: `ensureUrlToken(projectId | 'import')` mints (single-flight, memory only, renewed 10 min before expiry, counted from receipt so a wrong client clock does not matter) and `cachedUrlToken()` reads it; `blobUrl()` uses the cache, and `useUrlToken(projectId)` (`api/useUrlToken.ts`) keeps it and re-renders on renewal. Never put the access token or invite token in a URL. Browser tests: `e2e/url-tokens.spec.ts` (records every request/websocket URL). A script injected into the page could still use the in-memory token while the page is open, so **never inject untrusted HTML**.
- `auth/AuthProvider.tsx` resolves who this tab is (`loading | anonymous | guest | user`) via `/api/auth/me` or the invite's `resolve` endpoint. A change of identity goes to `loading` *immediately*; otherwise the catch-all route redirects on the stale identity (this bug made invite links land on /login). `useAuth()` exposes `signIn/signUp/signOut/leaveGuest`.
- `auth/useWorkspaceValue.ts` is the API-backed implementation of the design system's workspace contract: it loads `/api/workspaces`, remembers the active workspace per account, and wraps the member/role/invite/move calls. `guestWorkspaces()` builds the placeholder value for invite guests.
- `app/App.tsx` picks routes by auth status: anonymous → landing, `/login`, `/register`, `/collab` (everything else redirects to `/login?next=…`; `next` is only followed if it is a same-site path, see `safeNext`); guest → that one project's editor only; user → the full app, rendered only after workspaces load. Workspace roles are Owner / Admin / Editor / Commenter / Viewer (commenters read and comment, see *Comments*). Inviting an email with no account shows a pending "Invited" member, mails the invitation and becomes a membership when that address registers and verifies (see *Invitation mail*). The editor's collab provider takes `token: () => ensureUrlToken(projectId)` (awaited on every (re)connect).

**Compile contract.** `compileProject()` in `api/client.ts` hides the job protocol: it posts, polls `/api/jobs/:id` (1 s, 10 min cap), downloads the PDF, and resolves to `{ok, pdf(base64), log, status, focus}`, reporting progress via an optional callback (shown in the status bar). A reply without a `jobId` is a validation failure and is returned as is. In `EditorPage.tsx`, `compile()` first saves a live collaborative document (so line numbers match what the server compiles), records the preview's scroll position *before any await*, and hands the focus to `PdfPreview` through refs. `PdfPreview` scrolls to it after the pages render unless the reader scrolled meanwhile, otherwise restores the reader's place by ratio (also across zoom changes). Pitfalls: the render effect's own cleanup empties the container before the next run reads it, so the position is tracked in a ref from scroll events; and the compile shortcut must be bound inside CodeMirror at `Prec.highest`, because `basicSetup`'s default keymap binds Mod-Enter to "insert blank line" and sits ahead of the editor's own keymap.

**Editor language support (`latex/`).** Highlighting, environment/command completion, the structural linter (unmatched `\begin`/`\end`, braces, deprecated commands), hover docs, auto-close and folding come from **`codemirror-lang-latex`, which is AGPL-3.0-or-later** (the Overleaf Lezer grammar). The repo has no LICENSE file yet: decide the project's licence before distributing or hosting this for others (replacing the package means a permissive grammar such as `@codemirror/legacy-modes` stex plus our own sources). Our own code is `projectIndex.ts`: it indexes labels, bib keys and file paths from *all* text files (`getAllFiles`, refreshed after tree changes and saves; the live document overlays its own labels) and powers completion inside `\ref{}`, `\cite{}`, `\includegraphics{}`, `\input{}`, `\bibliography{}`, plus a warning for `\ref`/`\cite` keys nothing in the project defines. The package's single-file reference checks are switched off because they would flag every cross-file reference. Browser tests: `e2e/latex-intelligence.spec.ts`.

### Design system (`design/`)

All UI is built from the shared design system, imported as `@design` (alias in `apps/frontend/vite.config.ts` + `paths` in `apps/frontend/tsconfig.json`). Read `design/README.md` before touching UI. When building UI, follow the living style guide at `design/reference/design-system.html`.
- `tokens.css`: colour (light + dark via `data-theme` on `<html>`), type, spacing, radius, motion tokens and `op-`-prefixed component classes. Loaded first in `src/main.tsx`, before `App.css` and page CSS. If React code and the reference disagree on tokens, `tokens.css` is the source of truth.
- `Icon.tsx` / `iconPaths.ts`: the only icon source (`<Icon name="…" />`). Add new glyphs to `iconPaths.ts`.
- `ui.tsx`: `Button`, `IconButton` (label required), `Badge`, `Tag`, `Avatar`, `Menu`/`MenuButton`, `Select`, `SegmentedControl`, `Modal`, `PanelHeader`, `EmptyState`, `FieldError` (shared inline validation message).
- `AppTopBar.tsx` (shared top bar on every screen; workspace switcher + account menu, with a guest variant), `Logo.tsx`, `theme.ts` (`useTheme`), `AuthScreen.tsx` (sign-in / create-account).
- `workspace.tsx`: the **contract** between the UI and whatever supplies accounts/workspaces: types (`Workspace`, `WorkspaceRole`, `AccountUser`, …), `WorkspaceContextValue`, `<WorkspaceProvider value={…}>`, `useWorkspace()`. It knows nothing about the API; `apps/frontend/src/auth` supplies the real value. Action methods are async and reject with a user-presentable `Error`; components must handle the rejection (see `MembersSection` in `ProjectPage.tsx`).

Rules when writing UI:
- Use tokens (`var(--surface)`, `var(--text-2)`, `var(--accent)`…), never hex/rgba literals.
- Use `design/` components instead of new button/dropdown/menu styles (the old `btn` / `ios-btn` / `ios-select` / `ios-dropdown` / `toolbar-btn` / `icon-btn` families were removed). Allow one primary button per region.
- Never use emoji, text glyphs (✕ ▾ ▸ −) or pasted inline SVGs for icons.
- New strings go through `t('English text')`, with a matching entry in `src/i18n/locales/zh-CN.json`. English falls back to the key.
- `app/App.css` holds remaining legacy page styles (already mapped onto tokens). New page-level styles go in a page stylesheet such as `app/pages.css` or `app/editor-shell.css`.

`design/reference/` also has `index.html` (clickable prototype of the workspace home + editor shell), sharing `openprism.css` and `icons.js`. Open these directly in a browser; they are standalone HTML, not part of the Vite build.

### Templates (`apps/api/builtin_templates/`)

Built-in conference templates (ACL, arXiv, CVPR, ICML, NeurIPS) registered in `builtin_templates/manifest.json` (id, label, mainFile, category, bilingual descriptions, tags). They live inside `apps/api` so every API/worker image carries them (`settings.BUILTIN_TEMPLATES_DIR`). In the Django API, templates are `Template` rows with files in object storage; users upload custom ones as a ZIP via `POST /api/templates/upload`. `manage.py load_builtin_templates` (a wrapper over `import_legacy --skip-projects`) creates or refreshes the built-ins from the image; it is idempotent, rewrites only built-ins, and leaves a user template that happens to share a built-in's id alone. The Helm `migrate` Job runs it after `migrate` on every release (a fresh database gets the built-ins that way, #75); compose and CI load them with `import_legacy --skip-projects`/`load_builtin_templates` by hand.

### Kubernetes (`deploy/helm`, `deploy/bootstrap`, `deploy/caddy`)

The cent cluster already hosts Postgres, Redis and MinIO, so the chart `deploy/helm/openprism` deploys the app tier only: `api`, `web` (Service type **NodePort**, `nodePort` 31081; iot-portal uses 31080, graderthan 31801), `worker-compile`, `worker-transfer`, `worker-ai` (one template, `templates/workers.yaml`), `beat` and a per-revision `migrate` Job. No Ingress, NetworkPolicies, autoscaling or data services (the old kustomize tree with kind, ingress-nginx and KEDA was removed in v0.1.0; see git history). The workers have shutdown grace periods above their task time limits (360 s / 1900 s / 1000 s); `worker-compile` has no LLM credentials and `openprism-ai` is mounted only into `worker-transfer` and `worker-ai`. **Nothing restricts `worker-compile`'s network yet** (issues #111, #112; see the chart README's security model).
- **Release = a `vX.Y.Z` git tag** (`apps/api/VERSION` must equal it): `.github/workflows/deploy-cent-k8s.yaml` (self-hosted runner `[self-hosted, linux, cent]`, modelled on graderthan) builds `ghcr.io/cent-ischool/openprism/{api,web,worker-tex,worker-ai}:<tag>`, deploys with `helm upgrade --install --atomic --wait`, and smoke-tests the public URL (`deploy/smoke-release.sh`: `/api/health` must report the version). Never add a `pull_request` trigger to it: the repo is public and the runner is inside the cluster. `ci.yml` stays on GitHub-hosted runners for the same reason.
- **Credentials:** `deploy/bootstrap/bootstrap.sh` (run by the workflow only while Secret `openprism-app-creds` is missing, or alone via the "Bootstrap hosted services" workflow) uses the root `POSTGRES_*` repo secrets in a short-lived Job to create the `openprism` role (generated password) and database, and `s3-init.py` (plain S3 API via boto3, in the release's `api` image) to create the bucket and check the key pair; the generated/passed credentials are stored only in that cluster Secret and the chart reads `DATABASE_URL` and the S3 keys from it. The S3 API cannot create users, and the MinIO client `mc` is gone (dl.min.io 410, no pullable images; minio/mc is archived), so **the app uses the S3 key pair it is given: `OPENPRISM_S3_ACCESS_KEY/SECRET_KEY` if set, else the store's root key**. `DJANGO_SECRET_KEY`, `CREDENTIAL_ENCRYPTION_KEY` and `REDIS_PASSWORD` come from repo secrets via `--set-file`. Redis has no per-app role: the app uses database index 3 of the shared server.
- **Proxy:** Caddy2 (outside this repo, reference config `deploy/caddy/openprism.Caddyfile`) -> any node's NodePort -> web nginx -> api, so `TRUSTED_PROXY_COUNT` is 2 and `S3_DIRECT_UPLOADS` is 0 (MinIO is not browser-reachable).
- Checks: CI's `deploy-checks` job lints and renders the chart (`deploy/helm/openprism/ci/test-values.yaml`), validates the Caddyfile and runs ShellCheck. Run `helm lint` / `helm template` the same way locally. `deploy/helm/README.md` has the values, operating notes, security model and the list of what is still unverified.

### Devcontainer
